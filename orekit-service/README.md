# Orekit transfer service (optional JVM backend)

This is an **actual Orekit 13.1.9 dependency**, used to compute Lambert solutions with `IodLambert` and propagate the resulting Keplerian transfer orbit. It is intentionally a small **local** Java service, not a claim that a full NASA-quality mission simulator runs in JavaScript.

## Prerequisites

- Java JDK 17 or newer (recommend Temurin JDK 17)
- Apache Maven 3.9+ (on macOS with Homebrew: `brew install maven`)
- Network access on first build to download Orekit and its open-source dependencies

To build and test, from the repository root:

```bash
mvn -f orekit-service/pom.xml clean package
```

Start the service:

```bash
java -jar orekit-service/target/orekit-transfer-service-0.4.0.jar
```

Or double-click **`Start Orekit.command`** on macOS after installing Java and Maven.

Run the regular **`Start Space Race.command`** separately. The browser map works without the Java service; **Lambert transfer plotting and derived v-infinity/C3** require the Java service to be online.

## API

- `GET http://127.0.0.1:8787/health`
- `POST http://127.0.0.1:8787/api/lambert`

### Earth-orbit and trans-lunar injection propagation (v1.8)

The local Orekit Java service now implements **`POST http://127.0.0.1:8787/api/earth-orbit`**. It computes real Earth-centered two-body Keplerian propagation in EME2000, returning sample arrays of `[xKm,yKm,zKm]`, the orbital period, perigee and apogee radii and physical speeds.

Example request:

```json
{"perigeeAltitudeKm":400,"eccentricity":0.58,"argumentPeriapsisDeg":0,"inclinationDeg":0,"halfOrbit":false,"samples":181}
```

For a lunar-distance injection, use `perigeeAltitudeKm=400` and `eccentricity=(384400-(6378.137+400))/(384400+(6378.137+400))`, then `halfOrbit=true`. The frontend aims the argument of periapsis at an **approximate** mean lunar phase at first apogee; the Moon and spacecraft ARE NOT propagated as an n-body system. The endpoint has rigorous bounds and JUnit orbital closure/period/apogee checks. All backend calculations are independent of NASA API keys and do not need an external orekit-data directory for this two-body EME2000 model.

The Flight Directorate **requires neither Java nor network access** for Earth and lunar trajectories: it uses the shared TypeScript Kepler solver if the JVM is offline. For Mars/Jupiter with Java offline, it plots an explicitly labeled Sun-centered Hohmann conic rather than the former hand-drawn cubic path. An ideal Hohmann conic does not necessarily rendezvous with the moving planet.



Request example (from Earth and target position/velocity states generated by the frontend):

```json
{
  "departurePositionAu": [1,0,0],
  "arrivalPositionAu": [-1.3,0.8,0],
  "departureVelocityAuPerDay": [0,0.0172,0],
  "arrivalVelocityAuPerDay": [-0.0073,-0.0118,0],
  "flightDays": 260,
  "prograde": true,
  "samples": 128
}
```

The solver uses **JPL-derived approximate planetary positions** provided by the frontend (not mission-grade Horizons/SPICE ephemerides). Input position units: AU. Input velocity units: AU/day. The backend rotates ecliptic J2000 components into the Orekit EME2000 frame and applies a Sun-centered two-body gravitational parameter. It uses `AbsoluteDate.J2000_EPOCH` and relative timing, so no live leap-second or EOP dataset is needed in this educational model.

Returns a plotted transfer arc in heliocentric AU, Earth/target relative hyperbolic excess velocities in km/s, departure C3 in km²/s² and an endpoint propagation error.

**Critical caveats:** Departure v-infinity is NOT the actual delta-V needed from a low Earth parking orbit. Arrival v-infinity is NOT a capture burn. No gravity assists, staged launch trajectory, finite-thrust solar-electric integration, thrust duty cycle, n-body perturbations, eclipse, atmosphere, power-vs-distance optimization or launch authorization are handled. Numerical results are not valid for flight design or certification.

## Fixed-date Lambert flight-time optimization

The frontend can send up to 200 candidate arrivals for one departure date through:

- `POST http://127.0.0.1:8787/api/optimize`

Request schema: `{ target: "venus"|"mars"|"jupiter", objective: "departure"|"total", earthParkingAltitudeKm: number, targetParkingAltitudeKm: number, candidates: [ <same request as /api/lambert>, ... ] }`.

The frontend creates candidate arrival planetary position/velocity states using the JPL Table 1 approximate elements at each selected flight duration. The Java endpoint solves each with Orekit `IodLambert`, filters invalid candidates, computes cost, returns scores for each valid duration and a full Keplerian plotted trajectory for the lowest-cost candidate. The browser scans a coarse grid and refines the best sampled duration using one-day steps.

**Objective (ideal patched conics):** `Δv ≈ √(v∞² + 2μ/r) − √(μ/r)`. This is the burn from a circular parking orbit to a hyperbolic excess trajectory, or the equivalent ideal hyperbolic arrival circularization burn. JPL gravitational parameters are from https://ssd.jpl.nasa.gov/astro_par.html and reference radii from https://ssd.jpl.nasa.gov/planets/phys_par.html .

**Limitations:** Fixed departure date; only the sampled arrival-time/flight-duration range is optimized. Zero-revolution, prograde, impulsive two-body Lambert trajectories only. Planet positions and velocities use the browser's approximate JPL elements, not high-precision Horizons ephemerides. The Jupiter arrival circular orbit is conceptual (height measured from a 1-bar reference surface), not a recommended or operationally realistic close Jovian orbit. No ascent, parking-orbit orientation, gravity assists, atmospheres, aerocapture, orbit plane change, finite-thrust electric propulsion, spacecraft power, thermal capacity or mass budgeting. These are educational comparisons, not flight-ready trajectory optimizations.

**After GitHub Desktop pulls new code, stop and restart the Orekit launcher.** The JVM must be restarted to load the new endpoint.

## NASA/JPL historical spacecraft flight paths (v0.6)

Endpoint: `GET http://127.0.0.1:8787/api/heritage-track?mission=dawn`

Supported mission keys: `dawn`, `psyche`, `new-horizons`, `voyager`. The Voyager key specifically requests **Voyager 1**, Horizons spacecraft ID `-31`. The backend uses the requested mission's fixed date range and a sparse 30–90 day step to request Sun-centered ecliptic **position vectors in AU** from JPL Horizons `https://ssd.jpl.nasa.gov/api/horizons.api`. It caches successful fetches in memory for 12 hours.

This is a separate **internet-dependent** function, not an Orekit-computed historical path. Horizons may not return a usable vector table for an entire mission interval, and the 2D presentation hides out-of-plane motion. It shows sample-to-sample line segments only and a separate NASA milestone chronology if the remote response is unavailable. The game does not invent a closed historical orbit.

**After pulling changes, restart `Start Orekit.command`** so this endpoint is available. The service is local-only, and the fixed mission whitelist limits requests.

The service binds only to 127.0.0.1 and responds to local browser origins. It does not expose endpoints on the internet.

Orekit is Apache 2.0 open-source software: https://www.orekit.org/ . Further planetary accuracy work should replace client-side approximate elements with versioned NASA/JPL SPICE ephemerides and time-system handling.
